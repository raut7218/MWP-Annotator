# Database schema

This is the detailed reference for the Postgres schema behind MWP Annotator —
what each table is for, why it's shaped the way it is, and what changed in
the 2026-09-01 migration. For the short version, see the "Database schema"
section in [README.md](README.md).

The schema itself lives in one place, [`src/db.js`](src/db.js): every table
is created with `CREATE TABLE IF NOT EXISTS`, every later addition with
`ALTER TABLE ... ADD COLUMN IF NOT EXISTS` (or an equivalent existence check
for things Postgres has no `IF NOT EXISTS` for, like constraints). It all
runs on every boot, so there is no separate migration step to remember —
deploying is just restarting the process, on a brand new database or one
that's been running for a year.

## Design philosophy

Five tables, kept deliberately apart so that adding a model, a language, a
learning objective, or an annotator never requires reshaping anything else:

```mermaid
erDiagram
    users ||--o{ annotations : "writes"
    rows_data ||--o{ annotations : "is annotated by"
    learning_objectives ||--o{ rows_data : "generated from"
    learning_objectives ||--o{ learning_objective_texts : "worded in"

    users {
        serial id PK
        text username UK
        text password_hash
        text display_name
        text languages "JSON array"
        text models "JSON array"
        int is_admin "0/1, checked"
        int can_see_model "0/1, checked"
        int active "0/1, checked"
        timestamptz created_at
    }
    rows_data {
        serial id PK
        text model
        text language
        int row_index
        text grade
        text topic
        text question
        text answer
        text raw_response
        int parse_error "0/1, checked"
        int is_complete "0/1, checked"
        int lo_id FK "nullable"
        text lo_language
        text learning_objective
        text source_file
        timestamptz created_at
    }
    annotations {
        serial id PK
        int row_id FK
        int user_id FK
        int co_reference_issues "0/1, checked"
        int "...16 more flag columns" "each 0/1, checked"
        text comments
        text status "pending/reviewed, checked"
        timestamptz created_at
        timestamptz updated_at
    }
    learning_objectives {
        serial id PK
        text code UK
        text grade
        int ordinal
        timestamptz created_at
    }
    learning_objective_texts {
        serial id PK
        int lo_id FK
        text language
        text text
    }
```

`rows_data.id` is what `annotations.row_id` points at — the unique key
annotators actually work against is `(model, language, row_index)`, but once
a row exists its surrogate `id` is what everything else references.

## Table by table

### `learning_objectives` + `learning_objective_texts`

```sql
CREATE TABLE learning_objectives (
  id SERIAL PRIMARY KEY,
  code TEXT UNIQUE NOT NULL,        -- e.g. 'G3-LO1'
  grade TEXT NOT NULL,
  ordinal INTEGER NOT NULL DEFAULT 1,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE learning_objective_texts (
  id SERIAL PRIMARY KEY,
  lo_id INTEGER NOT NULL REFERENCES learning_objectives(id) ON DELETE CASCADE,
  language TEXT NOT NULL,
  text TEXT NOT NULL,
  UNIQUE(lo_id, language)
);
```

One objective, worded once per language. Example — objective `G3-LO2`, worded
in Māori and English:

| id | lo_id | language | text |
|---|---|---|---|
| 3 | 2 | Māori | ki te whiriwhiri i tētahi hautau waetahi... |
| 4 | 2 | English | Find a unit fraction of a whole number (eg ⅓ of 15)... |

Adding a third language for every objective is 6 `INSERT`s, not a schema
change — that's the entire reason this is two tables instead of a
`lo_text_maori`, `lo_text_english` column pair on one.

### `rows_data`

The generated problem itself — immutable source content, keyed by
`(model, language, row_index)`:

```sql
CREATE TABLE rows_data (
  id SERIAL PRIMARY KEY,
  model TEXT NOT NULL DEFAULT 'qwen',
  language TEXT NOT NULL,
  row_index INTEGER NOT NULL,
  grade TEXT,
  topic TEXT,
  question TEXT,
  answer TEXT,
  raw_response TEXT,
  parse_error INTEGER NOT NULL DEFAULT 0,
  is_complete INTEGER NOT NULL DEFAULT 0,
  lo_id INTEGER REFERENCES learning_objectives(id) ON DELETE SET NULL,
  lo_language TEXT,
  learning_objective TEXT,
  source_file TEXT,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE(model, language, row_index)
);
```

**Two source datasets share this one table, on purpose** (see the repo root
[README.md](../README.md)):

- `combined_qwen.xlsx` — Sinhala, Tamil, Punjabi, Odia, Marathi, Hindi
  problems (model `qwen`). These aren't tied to a learning objective, so
  `lo_id` is `NULL` for all of them — that's expected, not missing data.
- `MWPs/evaluation.xlsx` — Māori problems generated by five LLMs (`LLM1`…
  `LLM5`) from six learning objectives (two per grade, grades 3–5), each
  objective prompted in both English and Māori wording. These rows *do* carry
  `lo_id`, plus `lo_language`/`learning_objective` as a denormalized copy of
  which wording produced that specific problem (kept alongside the FK so
  exports don't need a join, and so the record survives even if the LO text
  is later edited).

`is_complete` marks whether a row has real generated content and should be
shown to annotators at all — rows where nothing was generated (blank cells,
an empty `{}` response) are imported but never surfaced. It is not a
guarantee that `answer` is non-empty: a truncated or failed generation can
still be "complete" in this sense, shown with a warning banner asking the
annotator to flag it, per the annotation guidelines, rather than hidden. If
you're querying this table directly, don't assume `is_complete = 1 →
answer IS NOT NULL`.

### `users`

```sql
CREATE TABLE users (
  id SERIAL PRIMARY KEY,
  username TEXT UNIQUE NOT NULL,
  password_hash TEXT NOT NULL,      -- bcrypt
  display_name TEXT,
  languages TEXT NOT NULL DEFAULT '[]',   -- JSON array, e.g. '["Māori"]' or '["*"]'
  models TEXT NOT NULL DEFAULT '[]',      -- JSON array, e.g. '["LLM1","LLM2"]'
  is_admin INTEGER NOT NULL DEFAULT 0,
  can_see_model INTEGER NOT NULL DEFAULT 1,
  active INTEGER NOT NULL DEFAULT 1,
  created_at TIMESTAMPTZ
);
```

Access to a model/language is the *intersection* of the two JSON lists
(`src/auth.js`): `"*"` in either list, or `is_admin`, means "all" on that
dimension. `can_see_model` is the per-account switch for whether an
annotator is shown which LLM produced a problem — real blinding, not
cosmetic: unless it's on, the model name never reaches the browser at all
(`src/models.js` addresses models by an HMAC ref instead).

`languages`/`models` are stored as JSON text rather than a join table or a
Postgres array deliberately, matching the small scale of this app (a
handful of annotator accounts): it keeps every access-control read a single
row fetch with no join, at the cost of not being queryable in SQL (`WHERE
'Māori' = ANY(languages)` isn't possible without parsing the JSON first). If
the annotator roster ever grows past a few dozen accounts with fine-grained
per-language assignment, that trade flips and a `user_languages(user_id,
language)` join table would be worth the extra join.

### `annotations`

One row per **(problem, annotator)** — this is the table that makes
independent double-annotation possible:

```sql
CREATE TABLE annotations (
  id SERIAL PRIMARY KEY,
  row_id INTEGER NOT NULL REFERENCES rows_data(id) ON DELETE CASCADE,
  user_id INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  co_reference_issues INTEGER NOT NULL DEFAULT 0,
  trivial_problem INTEGER NOT NULL DEFAULT 0,
  grammatical_errors INTEGER NOT NULL DEFAULT 0,
  misspellings INTEGER NOT NULL DEFAULT 0,
  incomplete_or_poorly_phrased INTEGER NOT NULL DEFAULT 0,
  unsolvable_problem INTEGER NOT NULL DEFAULT 0,
  unrealistic_scenario INTEGER NOT NULL DEFAULT 0,
  unit_issues INTEGER NOT NULL DEFAULT 0,
  topic_unsuitability INTEGER NOT NULL DEFAULT 0,
  not_satisfying_learning_objective INTEGER NOT NULL DEFAULT 0,
  not_a_word_problem INTEGER NOT NULL DEFAULT 0,
  ambiguity INTEGER NOT NULL DEFAULT 0,
  not_in_country_context INTEGER NOT NULL DEFAULT 0,
  wrong_or_missing_answer INTEGER NOT NULL DEFAULT 0,
  irrelevant_or_additional_info INTEGER NOT NULL DEFAULT 0,
  too_difficult INTEGER NOT NULL DEFAULT 0,
  code_mixed INTEGER NOT NULL DEFAULT 0,
  comments TEXT NOT NULL DEFAULT '',
  status TEXT NOT NULL DEFAULT 'pending',
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE(row_id, user_id)
);
```

`UNIQUE(row_id, user_id)` is the load-bearing constraint: it's what lets two
(or five) annotators be assigned the same sheet and each keep their own
flags without overwriting each other. The save endpoint
([`routes/rows.js`](src/routes/rows.js)) is an `INSERT ... ON CONFLICT
(row_id, user_id) DO UPDATE`, so re-saving the same problem always updates
that one annotator's row rather than creating duplicates.

The 17 flag columns are generated from a single list,
[`src/flags.js`](src/flags.js) — adding an 18th error category is one entry
in that file; `db.js` adds the column to every existing database on next
boot, no manual migration. This was chosen over a normalized
`annotation_issues(annotation_id, issue_type)` tag table because the flag
set is fixed and small (this is a closed annotation taxonomy, not
user-generated tags), and fixed columns let a single row express "here is
this annotator's complete verdict" without an aggregation query — the admin
export (`src/exportXlsx.js`) reads it as one row per annotation with no
`GROUP BY`.

### `session`

Standard [`connect-pg-simple`](https://www.npmjs.com/package/connect-pg-simple)
table (`sid`, `sess`, `expire`), created automatically by
`connectPgSimple(session)({ createTableIfMissing: true })` in
[`server.js`](server.js). Not part of the application's own schema.

## What changed on 2026-09-01, and why

Before this migration, every "boolean" column (`is_admin`, `active`,
`parse_error`, all 17 annotation flags, ...) was a bare `INTEGER` with
nothing in the database stopping an invalid value from being written —
only the application code's own discipline. `rows_data` and
`learning_objectives` had no timestamps at all, so there was no way to tell
when a problem was imported. `users.created_at` was `TEXT`, inconsistent
with `annotations`' proper `TIMESTAMPTZ` columns.

None of this was a live bug — every row in the database already satisfied
these rules, and the annotation-save path
(`INSERT ... ON CONFLICT ... DO UPDATE`) was already sound. But nothing
enforced the rules going forward, which is a real gap the moment a manual
`UPDATE`, a bug in a future feature, or a bulk import script writes
something malformed. The migration makes the existing convention a
guarantee instead of a habit:

- **`CHECK` constraints** added on every integer-boolean column
  (`users.is_admin/active/can_see_model`, `rows_data.parse_error/is_complete`,
  all 17 `annotations` flag columns) restricting them to `0`/`1`, and on
  `annotations.status` restricting it to `'pending'`/`'reviewed'`.
  Verified live: `UPDATE users SET is_admin = 5` and
  `UPDATE annotations SET status = 'nonsense'` are now both rejected by
  Postgres itself.
- **`users.created_at`** converted from `TEXT` to `TIMESTAMPTZ` (a lossless
  cast — every existing value was already a valid ISO-8601 string written by
  the app itself).
- **`created_at`** added to `rows_data` and `learning_objectives`, defaulting
  to `now()`. Existing rows backfilled to the migration's run time (their
  true import time wasn't recoverable from the data); every row from here on
  has a real one.

All of the above is additive/backward-compatible: no column was renamed or
removed, no existing app code changed behavior, and re-running it (e.g. on a
fresh environment) is a no-op — same idempotent pattern as the rest of
`db.js`.

### The connection-pooling bug this surfaced

Verifying the migration against the live database (rather than trusting the
`CREATE TABLE IF NOT EXISTS` boilerplate to just work) turned up something
more serious: **the app's own query pattern — unqualified table names like
`FROM rows_data` — failed outright** when run through Neon's pooled
connection endpoint:

```
SELECT count(*) FROM users;
ERROR:  relation "users" does not exist
```

The role's `search_path` comes back empty over that endpoint, and Neon's
pooler additionally refuses `search_path` as a startup parameter outright
(it errors with a message pointing at the unpooled connection instead of
silently ignoring it). Since **every** query in this codebase
(`rows.js`, `admin.js`, `auth.js`, `db.js`) uses unqualified table names,
this isn't an annotations-only problem — it would break login and every
read too, on whichever connection string actually exhibits it.

Fixed in [`src/db.js`](src/db.js) by overriding the pool's per-connection
`Client.connect()` to run `SET search_path TO public` before the connection
is considered ready — not a `pool.on('connect', ...)` listener, which fires
without the pool waiting for it and lets the first real query race the fix
(confirmed this the hard way: the naive version produced a
"query already in progress" error under load). This makes the app behave
identically regardless of which connection string variant (pooled or
direct) it's handed, so it can no longer depend on which endpoint someone
copied out of the Neon dashboard.

## Verification

The full migration was tested against a running instance before being
considered done:

1. Backups taken first — a local CSV export of every table
   (`app/backups/`, gitignored) and a live in-database snapshot schema
   (`backup_pre_migration_<timestamp>`) inside the same Neon database, both
   verified to have identical row counts to `public` before any change.
2. Migration applied by booting the app itself against the live database
   (the same `db.js` code path a real deploy runs), not a one-off script.
3. Logged in through the actual UI, opened a real problem, checked a flag,
   added a comment, and saved — confirmed via direct SQL that the row
   landed correctly in `annotations` alongside the pre-existing real
   annotator's independent row for the same problem.
4. Confirmed the new constraints actually reject bad data (see above), not
   just that they exist.
5. All test data (a temporary account, one test annotation) removed
   afterward; final row counts confirmed to exactly match the
   pre-migration backup.

## Known gaps (not fixed by this migration, on purpose)

- `learning_objective_texts` only has Māori/English wording. The six
  non-Māori annotation languages (Hindi, Marathi, Odia, Punjabi, Sinhala,
  Tamil) have no learning-objective text to join against — not a bug, since
  those rows never had one (see `rows_data`, above), but worth knowing if
  you're writing a new query that assumes every row has an LO.
- `users.languages`/`models` remain JSON-in-text rather than a join table —
  a deliberate scale trade-off (see `users`, above), not an oversight.
- 61 rows currently have `is_complete = 1` with an empty `answer`. This
  reflects real source data (truncated/failed generations that are still
  shown to annotators per the guidelines, not a data-entry error), so no
  `CHECK` was added enforcing "complete implies answered" — doing so would
  assert something false about existing, intentional rows.
